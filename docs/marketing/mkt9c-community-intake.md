# MKT9.C — Community intake candidate
Status: implementation draft; dependent on MKT9.B #1585; never enable until all gates below pass.

## UX
Two non-binding interest lanes, partner and investor, in IT/EN. No account or purchase required. Three fields (name, email, organization required only for companies), privacy acknowledgment, anti-bot challenge. No newsletter opt-in, funding amounts, documents, tax IDs, phone or arbitrary message. Closed fallback remains the existing email contact.
The existing owner-only fundraising console shows separate real counts, recent requests (100 max), status and confirmed deletion. Contacted investor requests can prefill the existing MKT8 CRM, but an owner must verify identity/email and check for duplicates before saving. No automated promotion, email sending, invite, membership, payment or equity offer. Email possession is not verified by the challenge.

## Security and deployment
- The application defaults closed. Server action checks legal identity, approved notice version, explicit enable flag and CAPTCHA configuration; validates token via Siteverify, expected hostname/action, timeout. No raw token or contact data in logs. Duplicate email per lane or challenge digest is rejected by unique constraints with a uniform response.
- Proposed schema is `docs/marketing/mkt9c-community-interest-schema.candidate.sql`, NOT a Supabase migration. Generate actual migration with local CLI only after disposable acceptance; do not execute against production. RLS owner-only reads/updates/deletion; no anon writes. Service-role key is server-side only and must be configured via protected environment, never pasted into chat or committed. Consider narrowly scoped RPC/credential instead before approval; service-role credentials have broader platform powers.
- Required env names (no values): MKT9_COMMUNITY_INTAKE_ENABLED, MKT9_COMMUNITY_NOTICE_APPROVED, MKT9_TURNSTILE_SITE_KEY, MKT9_TURNSTILE_HOSTNAME, MKT9_TURNSTILE_SECRET, MKT9_COMMUNITY_SUPABASE_SECRET. Set explicit enabled flag only after all gates and approved notice revision. Rebuild static project/investor pages when changing flags.
- Test real JWT roles (anon, regular user, staff without owner, owner, service role), insert only, duplicate cross-lane rules, concurrent challenge replay, owner mutation, delete, expired records, fail closed provider/db. Exercise browser 320/390/1440, keyboard and screen reader, localized feedback, CAPTCHA/CSP and provider failure. Verify no PII in analytics, logs, redirect URLs or artifact uploads; review provider privacy obligations.
- The current privacy policy is provisional and does not describe this new intake. Draft notice requirements: controller identity/contact; request handling purpose and approved legal basis per lane; fields, recipients/processor and transfers including CAPTCHA; retention and rights; no marketing without separate basis. Proposed 90-day retention for unresolved requests is NOT approved: implement a documented purge schedule and deletion workflow (including CRM copies and backup handling) before activation. Notice version in code/schema is candidate, revise together with approval. No claim of compliance.
- Verify actual email ownership before trusting or adding to verified pipeline; if scale requires automated verification, design a separate rate-limited opt-in step (avoid unsolicited confirmation abuse). Owner dashboard clearly labels unverified addresses.
- CI source contracts are not a real database or browser test. MKT9.A and B must be released in protected sequence. This PR may include B commits until #1585 lands; review only C delta relative to B. No production change, data collection or payments during draft.
