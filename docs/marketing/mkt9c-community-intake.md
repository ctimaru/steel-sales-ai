Status: implementation draft; dependent on MKT9.B #1585; never enable until all gates below pass.

## UX
Two non-binding interest lanes, partner and investor, in IT/EN. No account or purchase required. Three fields (name, email, organization required only for companies), privacy acknowledgment, anti-bot challenge. No newsletter opt-in, funding amounts, documents, tax IDs, phone or arbitrary message. Closed fallback remains the existing email contact.
The existing owner-only fundraising console shows separate real counts, recent requests (100 max), status and confirmed deletion. Contacted investor requests can prefill the existing MKT8 CRM, but an owner must verify identity/email and check for duplicates before saving. No automated promotion, email sending, invite, membership, payment or equity offer. Email possession is not verified by the challenge.

## C.2 — Email ownership candidate (supersedes earlier no-email design)
- User submits minimal details, CAPTCHA validated server side. Atomic service-only SQL reservation checks token replay, max 1 send/10 minutes per keyed email digest, max 3/day per digest and global 60/hour; no provider send unless reservation returns true. Eight-digit cryptographically random code, HMAC with server-only secret, 10-minute validity, five wrong attempts. Only a valid confirmation creates a lead; confirmation locks the pending row, consumes it and does not overwrite duplicates. Raw code is sent via transactional Resend, not stored in DB or logged; no marketing. HttpOnly Secure same-site cookie carries opaque request UUID; no email/code in URL. Receipt requires a successful action cookie. Code confirms control of mailbox, not individual identity or company authority. Provider acceptance/delivery not yet tested.
- Pending PII is short-lived and separate from CRM; purge candidate additionally deletes expired pending rows and rate digests older than 24h. Before activation schedule cleanup every 15 minutes (including bounded leads deletion or separate jobs), monitor failures and backlog, review Resend logs/retention and backup cycle. Proposed limits require founder validation; initial global cap deliberately conservative. Do not set approvals until verified.
- New env names: MKT9_COMMUNITY_OTP_SECRET (random >=32 chars), MKT9_COMMUNITY_EMAIL_FROM (approved sender), RESEND_API_KEY (already used elsewhere, prefer narrowly scoped send-only credential), MKT9_COMMUNITY_MAILBOX_VERIFIED, MKT9_COMMUNITY_CREDENTIAL_APPROVED (both exact approved notice version). Current draft notice version is hard-blocked even if flags are set. Service-role candidate still has broad privileges: minimum-privilege architecture remains an opening gate.
