## Phase A: Auth bootstrap (manual only)

1. In GitHub Actions secrets, store the 14 existing \`RQG32_*_EMAIL\` and \`RQG32_*_PASSWORD\` values expected by RQG3.2. Emails must EXACTLY match the seven in the table. Set \`RQG32_COMPANY_A_MARKER=RQG32-ORG_A-20261013\` and \`RQG32_COMPANY_B_MARKER=RQG32-ORG_B-20261013\`.
2. Supply \`RQG32A_AUTH_SECRET_KEY\` through **private GitHub Actions Secrets** only, ideally an independently rotated Supabase secret key dedicated to the short-lived QA run. It bypasses RLS: restrict GitHub Actions permission, revoke it after completing provisioning; never paste it into ChatGPT, Notion, a PR or user-visible logs. Do not use the sole Platform Owner's password.
3. Run **RQG3.2a Controlled Production Test Personas** manually on \`main\` with \`mode=preflight\` and exact approval phrase \`RQG32A_INSPECT_SYNTHETIC_USERS\`. This requires the secret for trustworthy account/owner preflight but makes **zero writes**.
4. After verifying preflight, run \`mode=create\` with \`RQG32A_CREATE_SEVEN_SYNTHETIC_USERS\`. Only \`auth.admin.createUser()\` is called, once per missing account. Existing correctly tagged users are never overwritten; passwords are not rotated and neither credentials nor session state are uploaded.
5. Run \`mode=verify\` with \`RQG32A_INSPECT_SYNTHETIC_USERS\` to confirm exactly seven tagged identities and exactly one active Platform Owner.

If any step fails, stop and inspect the named QA users in Supabase Auth admin. Partial creation is safe to rerun only after collision diagnosis; no rollback or delete is automatic.
